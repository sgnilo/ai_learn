# 开源项目研读路线

返回：[开源项目研读](./00-overview.md) / [AI 学习](../ai/00-overview.md) / [全栈学习](../full-stack/00-overview.md) / [Progress](../progress.md)

## 目标

这条支线训练的不是“读代码速度”，而是五项可以迁移到陌生代码库的能力：

1. 从产品目标和运行入口建立系统地图。
2. 沿调用链追踪控制流、数据流和状态变化。
3. 从测试、配置和错误路径反推系统边界。
4. 用运行实验验证对源码的解释。
5. 识别设计取舍，并将其迁移到自己的工程实践。

## 项目选择

一次只研读一个项目。候选项目优先满足：

- 与 AI 或全栈主线的当前问题直接相关。
- 能在本地运行最小路径，或至少拥有可执行测试。
- 有清晰入口和较好的测试，能够形成证据闭环。
- 规模允许先在 1～2 次会话内读通一条纵向切片。
- 许可证允许学习和本地实验。

不要因为 star 数高就选择项目，也不要一开始挑战整个大型 monorepo。大型项目必须先限定到一个 package、命令或请求路径。

## 单项目学习闭环

### 1. 定义问题

将“看看这个仓库”收敛为一个可验证问题，例如：

- 一次 HTTP 请求如何从监听端口走到业务 handler？
- Agent 的一次 tool call 如何被解析、执行、记录并返回给模型？
- 一条任务失败后，状态如何持久化并恢复？

### 2. 建立仓库地图

先确认版本基线、语言与构建系统，再定位：

- 程序入口与公开接口
- 核心 package / module
- 配置、状态和外部 I/O 边界
- 与目标路径最相关的测试

仓库地图只需支持本轮问题，不追求覆盖全部目录。

### 3. 追踪纵向切片

从外部输入出发，记录每一跳的文件、符号、输入输出和关键状态变化，直到可观察结果。优先读真实实现和对应测试；文档用于建立假设，不作为最终证据。

### 4. 运行验证

至少完成一种验证：

- 运行相关测试并解释断言覆盖了什么。
- 增加日志或断点观察调用顺序与数据形状。
- 做一个可撤销的最小改动，预测并观察行为变化。
- 构造失败输入，确认错误传播和恢复路径。

如果项目无法运行，要明确记录阻塞原因，并用测试、静态调用关系或历史证据降低不确定性。

### 5. 复述与迁移

学习者应能够脱离源码回答：入口在哪里、核心抽象负责什么、状态在哪里变化、为什么这样设计、失败时会发生什么。最后提炼一项能用于当前 AI 或全栈实践的结论。

## 深度等级

| Level | 完成标准 |
| --- | --- |
| L0 · 定位 | 能说明项目解决的问题、运行入口和主要模块 |
| L1 · 路径 | 能用文件与符号证据讲清一条端到端调用链 |
| L2 · 验证 | 能运行测试或实验验证调用、状态与错误路径 |
| L3 · 取舍 | 能解释关键设计选择、替代方案和适用边界 |
| L4 · 迁移 | 能在自己的实现中复现该模式，并说明调整原因 |

每个项目至少达到 L2 才算完成一轮研读。是否继续到 L3/L4，由它与当前主线的相关度决定。

## 每次会话的节奏

一次会话只推进一个明确问题：

1. 回顾上次结论或定义本次问题。
2. Agent 给出最小仓库地图和建议入口。
3. 共同读通一段调用链，学习者先预测关键行为。
4. 运行一个验证实验。
5. 学习者复述，Agent 纠偏并更新研读笔记。
